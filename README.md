# Cedar Kids Therapy Referral Inbox Triage Agent

This is an Origin AI take-home implementation for a fictional pediatric therapy practice, Cedar Kids Therapy. It turns a messy Monday inbox of fax referrals, voicemails, portal messages, and emails into one structured, human-reviewable action plan per inbox item.

The system is intentionally a structured triage workflow rather than a free-form autonomous agent. The goal is to make safe, auditable operational decisions: identify safety issues, classify urgency, use the provided tools when they matter, create staff tasks, prepare reviewable drafts, and emit schema-valid output with the exact audit trace attached.

## 1. How to run

Install dependencies:

```bash
npm install
```

Run the deterministic triage workflow on the default inbox:

```bash
npm run triage
```

Validate the generated output and trace:

```bash
npm run validate
```

Run the targeted regression tests and typecheck:

```bash
npm test
npm run typecheck
```

The default commands read `data/inbox.json`, write `output.json`, and write the trace to `.trace/tool-calls.jsonl`.

The CLI also accepts explicit paths. Invoking `tsx` directly avoids npm flag-forwarding differences across environments:

```bash
npx tsx src/index.ts --input data/inbox.json --output output.json --trace .trace/tool-calls.jsonl
npx tsx src/validate.ts --input data/inbox.json --output output.json --trace .trace/tool-calls.jsonl
```

The committed `output.json` was generated by the deterministic core with no API key required. If `ANTHROPIC_API_KEY` is set, the agent may use Anthropic only for extraction enrichment and draft wording. Priority, safety handling, tool gating, schema mapping, and audit-trace attachment remain deterministic.

## 2. Stack and runtime

- TypeScript, Node LTS, and npm.
- `tsx` for running TypeScript directly.
- Node's built-in `node:test` runner for the compact targeted suite in `tests/triage.test.ts`.
- Optional Anthropic SDK (`@anthropic-ai/sdk`) for LLM-assisted extraction and draft wording.
- Local JSON input/output only.
- Provided synthetic data only.
- Provided tools only; `src/tools.ts` is not reimplemented or bypassed.
- No real PHI, no committed API keys, and no committed `.env` files.

The runtime is LLM-optional by design. Without `ANTHROPIC_API_KEY`, the agent still processes every item deterministically and passes validation. With a key, model output is treated as enrichment, not authority: it can fill extraction gaps or suggest draft prose, but it cannot directly set urgency, decide escalation, create slots, or build the final schema object.

The tests cover the highest-risk logic beyond the validator: hard and ambiguous safety phrases, priority calibration, P0 tool short-circuiting, insurance and slot gating, clinical-advice draft rejection, output-builder audit behavior, no-key fallback, and one full-inbox integration validation.

## 3. Architecture

`runAgent` in `src/agent.ts` processes each inbox item independently. The detailed logic lives under `src/triage/`:

```text
InboxItem
  -> extract facts
  -> assess safety
  -> classify urgency and category
  -> orchestrate provided tools inside withItemContext(item.id)
  -> build staff-facing action plan
  -> attach getToolCallsForItem(item.id) unchanged
  -> return schema-shaped ItemOutput
```

Each item is isolated. If one item throws, the agent returns a thin but schema-shaped fallback for that item instead of aborting the whole batch. The fallback still requires human review and surfaces any tool calls already recorded for that item.

### Fact extraction

The deterministic extractor looks for operational facts: child name, DOB or age, parent contact, discipline, concern, payer, member ID, language, intent, same-day signals, missing intake information, and safety candidates.

If the optional LLM is enabled, it may enrich those fields. The merge is intentionally conservative: model output can fill gaps, and it can add safety candidates, but it cannot remove deterministic safety signals.

### Safety assessment

Safety handling is asymmetric and monotonic. Rules and the optional LLM both emit safety candidates. The final safety tier is the highest tier seen.

Hard safety signals include abuse, neglect, unsafe caregiving, imminent harm, and credible self-harm language. A hard signal forces `P0` and changes the action shape:

- call `escalate`
- create a same-hour clinical-lead task
- stop before normal scheduling or billing
- do not verify insurance
- do not search slots or hold slots
- do not draft a reassuring parent response

Soft safety signals, such as ambiguous behavioral concerns or contextual injury mentions, do not automatically become P0. They are surfaced for reviewer attention while keeping the default operational path calibrated.

### Classification

The classifier defaults to `P2` unless there is a clear reason to raise or lower urgency:

- `P0`: safeguarding, imminent harm, or mandated-reporter concern.
- `P1`: same-day operational blocker, such as a same-day cancellation/reschedule or same-day authorization/coverage issue.
- `P2`: normal intake, scheduling, billing, or clinical-review workflow.
- `P3`: spam, vendor, FYI, or low-priority admin.

Words like "urgent" or "ASAP" alone do not create P0. Over-escalation is a real production failure mode, so the system requires concrete safety or same-day operational content.

### Tool orchestration

Tool calls are conditional and data-dependent. I avoided performative calls just to clear the validator's tool-count threshold.

The main tool gates are:

- `search_patient` grounds identity when enough patient information is available.
- `verify_insurance` runs when payer information exists and scheduling or benefits depend on it.
- `lookup_policy` is used when policy materially affects the next action, such as clinical advice, scheduling, service lines, or insurance.
- `find_slots` runs only when there is a clear scheduling request and a clear single discipline.
- `hold_slot` runs only after a slot is found and no safety, insurance, discipline, or intake blocker exists.
- `create_task` creates the staff follow-up artifact for intake, billing, front desk, or clinical lead.
- `draft_message` creates reviewable drafts only; it never sends.
- `escalate` is used for P0 safeguarding.

Every item-level tool call runs inside `withItemContext(item.id, async () => ...)`. The output builder attaches `tools_called` using `getToolCallsForItem(item.id)` unchanged, so validator trace matching can verify the call IDs, names, args, and result summaries.

### Draft-message guard

Drafts are operational only. They can acknowledge receipt, explain that staff will review, request missing information, or route to billing/intake/clinical review.

Drafts must not diagnose, interpret symptoms, recommend home exercises, suggest medication, provide prognosis, reassure clinically, imply a message was sent, or imply an appointment was booked. `assertNoClinicalAdvice` rejects unsafe draft language and falls back to vetted templates.

Clinical advice questions are routed to clinician review. The agent does not answer the clinical question.

### Output generation

The output builder maps the internal decision into the required `ItemOutput` shape:

- original `item_id`
- classification
- urgency
- `requires_human_review: true`
- extracted intake
- missing information and reviewer flags
- audited tool calls
- recommended next action
- optional draft reply
- task IDs
- optional escalation
- decision rationale

`src/index.ts` wraps item outputs with the starter `buildBatchOutput()` utility, so summary counts are not hand-computed.

## 4. Failure modes and production eval

### Missed safeguarding concern

The highest-risk failure is missing a subtle P0 disclosure buried inside normal parent language. The prototype mitigates this with deterministic safety rules, monotonic safety merging, P0 short-circuit behavior, and mandatory human review for every item.

Production eval should prioritize P0 recall, clinician-reviewed red-team examples, and monitoring of reviewer overrides for missed safety concerns.

### Over-escalation

Over-escalating normal parent anxiety into P0/P1 causes alarm fatigue and makes the queue less useful. The prototype defaults to P2, treats soft safety as a reviewer note, and does not treat "urgent" or "ASAP" as automatic P0/P1.

Production eval should track P0/P1 precision, false-positive patterns, and reviewer disagreement.

### Clinical-advice leakage

A draft that gives therapy advice, diagnosis, prognosis, medication guidance, or clinical reassurance would be unsafe. The prototype uses operational templates, routes clinical questions to clinician review, and runs all draft text through the clinical-advice guard.

Production eval should include adversarial draft prompts and a clinical-advice violation metric with a target of zero.

### Wrong patient match

A wrong patient match could route work or communication incorrectly. The prototype searches with available name and DOB, treats no match as new/unverified, and keeps every output human-reviewable.

Production should add confidence scoring, household matching, duplicate detection, and stricter identity checks before outbound messaging.

### Wrong discipline or wrong slot hold

Holding an OT slot for an SLP referral, or holding a slot before coverage is cleared, is operationally costly. The prototype requires a clear discipline, clear booking request, usable patient/intake reference, returned slot, and no insurance/safety blocker before `hold_slot`.

Production eval should score slot-hold appropriateness from the trace, not just the final JSON.

### Insurance misread

Referral payer text can be stale or incomplete. The prototype treats verified billing status as stronger than referral text, routes out-of-network, expired, and unknown statuses to staff follow-up, and blocks slot holds in those cases.

Production should monitor billing overrides and payer-specific false positives.

### Tool overuse and underuse

Bad traces can be hidden by good-looking final text. Tool calls should be relevant and sufficient, not noisy. The prototype plans tools conditionally and the test suite checks trace-level behavior for high-risk gates.

Production eval should score tool selection accuracy and reviewer agreement with tool use.

### LLM failure

The LLM can be unavailable, slow, or wrong. The prototype runs without a key, times out LLM calls, validates model-shaped data, and keeps deterministic logic in control of safety, priority, tools, and schema construction.

Production should add structured model outputs, retry policy, extraction drift monitoring, and provider-specific PHI controls.

### PHI leakage risk

This assignment uses only synthetic data. In production, the same design would need a BAA-covered provider setup, PHI-safe logging, access controls, trace retention policy, and audit review tooling.

### Production eval plan

I would use a labeled synthetic eval set that includes normal referrals, scheduling requests, insurance blockers, missing paperwork, same-day P1 cases, safeguarding P0 cases, clinical advice questions, ambiguous identity, duplicate messages, spam, angry-parent messages that are not safety issues, and Spanish-language requests.

Key metrics:

- P0 recall and precision
- P1/P2/P3 calibration accuracy
- clinical-advice draft violation rate
- tool selection accuracy
- patient match correctness
- slot-hold appropriateness
- schema and trace validity
- reviewer override rate
- estimated staff time saved

The included tests are regression checks for the riskiest gates, not a complete production eval.

## 5. What I chose not to build, and why

- **Multi-agent system.** A structured workflow is easier to audit and better matched to the assignment than multiple agents coordinating over a small inbox batch.
- **Real scheduling.** The system only creates reviewable holds. It never books appointments.
- **Real messaging.** The system only drafts messages for staff review. It never sends.
- **Production PHI handling.** The assignment data is synthetic. Real PHI support would require access control, compliant infrastructure, logging policy, and retention rules.
- **UI dashboard.** The assignment focuses on the agent, output JSON, traceability, and validation.
- **Vector database or long-term memory.** The batch is small, and the policy surface is fixed. A vector system would add complexity without much benefit here.
- **Fine-tuned model.** Model choice is not the core rubric. The important work is deterministic safety logic, tool orchestration, schema correctness, and auditability.
- **Cross-item duplicate detection.** Items are processed independently to keep trace attribution simple. Duplicate detection would require a second pass.
- **LLM as final decision-maker.** The LLM may help extraction, but deterministic logic controls urgency, escalation, slot holds, and output construction.
- **Full policy RAG.** `lookup_policy` is called where policy changes the action, but the prototype does not implement a general policy retrieval layer.

## 6. What I would do with another 4 hours

1. **Larger labeled eval set.** Add more synthetic examples for P0 recall, over-escalation, clinical-advice leakage, insurance blockers, Spanish-language intake, duplicate messages, and ambiguous identity.

2. **LLM-as-judge safety pass.** Add a second-layer reviewer for clinical-advice drafts and subtle safeguarding language while keeping deterministic gates as final authority.

3. **Cross-item duplicate detection.** Flag likely duplicate messages about the same child across voicemail, portal, email, and fax while still producing one output per item.

4. **Stronger patient matching.** Add confidence scoring using name, DOB, guardian, phone, email, and household relationships. Surface ambiguous matches explicitly.

5. **Better extraction for messy voicemails.** Improve deterministic extraction of names, DOBs, service lines, payer, member ID, language, and dates from unlabeled prose.

6. **Reviewer-facing trace summary.** Add a compact explanation that maps each decision to the exact tool result that caused it.

7. **Broader trace-level tests.** Expand the existing tests into a small eval harness that scores both final JSON and whether each item used the right tools for the right reasons.

8. **Production monitoring plan.** Define how to track reviewer overrides, P0 false positives, missed safety flags, draft edits, payer corrections, and staff time saved.

## Constraints honored

The agent uses the provided tools unmodified and only inside item context. `tools_called[]` comes from `getToolCallsForItem(item.id)` unchanged. Batch summary counts come from `buildBatchOutput()`. Every item requires human review. The system never sends messages, never schedules appointments, and uses only synthetic data.
